# Pulse 5.4.12 Backup and Recovery Integrity Design

## Goal

Release Pulse 5.4.12 so every backup, EOD completion, live download, history export, migration snapshot, and historical report is honest about its source and verified before success is claimed. Preserve 5.4.10–5.4.11 financial and security controls.

## Scope

In scope:

- Replace header-only backup health with verified SQLite integrity.
- Dual verified EOD backup packages: pre-purge required, post-purge required.
- Consistent online-backup copies for live download and full-history export.
- Fail-closed migration pre-snapshots.
- Complete backup package coverage: ops DB, inventory DB, incident attachments, store-transfer documents, and manifest.
- Honest historical-report source labeling with no live-DB fallback under a BACKUP label.
- Additive migration 061 and full test coverage through packaging.

Out of scope (later releases):

- 5.4.13 incident-investigation immutability, signature authority, inventory-count permissions, committed-backstock consistency.
- 5.4.14 spreadsheet parser replacement and dependency audit cleanup.

## Policies Chosen

1. **EOD:** verified pre-purge package required to proceed; verified post-purge package required for success.
2. **Sidecars:** every verified package bundles ops + inventory + incident attachments + store-transfer docs + manifest.
3. **Migrations:** fail closed until a verified pre-migration package succeeds.

## Architecture

Introduce one authoritative backup package pipeline consumed by health, EOD, maintenance download, history export, migration safety, and reports. Call sites do not invent their own copy/verify rules.

Primary new/extended modules:

- `src/lib/backup-package.cjs` — create, verify, and describe packages.
- `src/lib/backup-health.cjs` — health derived from verification, not header alone.
- `src/lib/migration-safety.cjs` — verified snapshot with fail-closed default.
- `src/api.cjs` / EOD path — dual-stage backup around destructive work.
- `src/dal/reports-payload.cjs` / reports routes — fail closed on unavailable backup source.
- Migration `061_backup_integrity_controls.cjs` — durable EOD backup status/error fields as needed.

## Verified Package Contract

A verified package is created as follows:

1. Create a working directory under the configured data root backups area.
2. Copy `tgp_ops.db` using better-sqlite3 online `backup()` (not raw file copy of a live WAL database).
3. Open the copied ops DB read-only and run `PRAGMA quick_check` (and `integrity_check` when practical for drills/deep verify).
4. Include `pulse_inventory.db` when present (consistent copy; empty/absent noted in manifest).
5. Include `data/incident_investigations/**` attachment trees when present.
6. Include `store-transfers/**` generated documents when present.
7. Write `manifest.json` containing:
   - package id / filename stem
   - stage: `pre_eod` | `post_eod` | `manual` | `migration` | `weekly` | `history_export`
   - created_at
   - actor when known
   - relative paths, byte sizes, and content hashes for each included artifact
   - verification results for the ops DB copy
8. Promote the package only after verification succeeds.

A file that contains only a valid SQLite header is **not** healthy.

## Backup Health

- `getBackupHealth` / sync / readiness use verification outcome, not header-only readability.
- Header checks remain a fast reject for non-SQLite files.
- Deep drill (`inspectBackupDatabase` / verify-backup) remains available and must agree with package verification for the ops DB.
- Readiness treats missing/unverified latest backup as blocking or warning per existing aggregation rules, but must not report false health for header-only files.
- Rewrite `tests/backup-health.test.cjs` so the previous false-positive contract is inverted.

## EOD Flow

```text
pre-verified package
  -> destructive archive / retention purge / day stamp transaction
  -> post-verified package
  -> success
```

Rules:

- If pre-purge package creation or verification fails: abort. No destructive purge. No day-complete success. Return structured error `EOD_PRE_BACKUP_REQUIRED` / `BACKUP_VERIFICATION_FAILED`.
- If destructive stage fails: existing transactional rollback behavior remains; no success.
- If post-purge package fails after destructive stage committed: do **not** return EOD success. Persist durable error/status fields (migration 061). Leave catch-up/UI able to see that backup is incomplete. Return `EOD_POST_BACKUP_REQUIRED`.
- Manual EOD and missed-sweep catch-up use the same contract.
- API responses include backup package identifiers/stages when successful.

## Live Download and History Export

- `POST /api/backup-db` and history-export DB inclusion must use the verified package pipeline (or a verified ops copy produced by it).
- Never `res.download(getDbPath())` of the live main file while WAL may be active.
- Never ignore checkpoint/copy failure and continue as success.
- History export fails the request if the database artifact cannot be verified.

## Migration Snapshots

- Before applying pending migrations, create a verified package with stage `migration`.
- Default is fail closed (`failOnError: true` in production boot path).
- If snapshot/verification fails, do not apply pending migrations.
- Snapshot packages use a distinct `migration` stage/name prefix and remain discoverable for recovery tooling. They are never listed or labeled as daily EOD backups.

## Historical Reports

- When a client requests `?backup=<file>` (or equivalent), the server must successfully open that backup artifact.
- On missing, unreadable, or failed verification: HTTP 4xx with `BACKUP_SOURCE_UNAVAILABLE` (or equivalent stable code). No live DB substitution.
- `reportSource` / BACKUP UI chrome may be set only after successful open of the requested backup.
- Daily and weekly backup naming must both resolve to honest source metadata.
- Regression for the proven case: request a missing `2026-07-01` backup → error, not live data labeled BACKUP.

## Error Contract

| Code | Typical HTTP | Meaning |
|------|--------------|---------|
| `BACKUP_VERIFICATION_FAILED` | 500/400 | Copy or integrity check failed |
| `EOD_PRE_BACKUP_REQUIRED` | 500/409 | EOD aborted before purge |
| `EOD_POST_BACKUP_REQUIRED` | 500/409 | Purge committed but post package failed; day not successfully completed |
| `BACKUP_SOURCE_UNAVAILABLE` | 404/400 | Historical report backup missing/corrupt |
| `MIGRATION_SNAPSHOT_REQUIRED` | boot/500 | Pending migrations blocked |

Messages must identify remediation without claiming a backup exists when verification failed.

## Migration 061

Additive and idempotent. Intended fields (exact names may match existing schema style):

- EOD/backup status columns or settings needed to record last successful pre/post package ids, timestamps, and last backup error.
- Indexes only if required for lookup.
- No rewrite of existing backup files during migration.
- Existing header-only junk files become unhealthy after upgrade; operators re-run EOD/manual verified backup.

## UI / Operator Surface

- Maintenance backup/download/export flows surface verification failures clearly.
- Reports UI shows a real error when a selected backup cannot be opened (no silent live fallback).
- Deploy notes state that 5.4.12 packages include inventory, attachments, and transfers, and that historical BACKUP views require a real backup file.

## Test Strategy

Every behavior change is red-green. Minimum coverage:

1. Header-only SQLite file is unhealthy.
2. Verified package includes ops, inventory, attachments, transfers, and manifest hashes.
3. EOD aborts before purge when pre-backup fails; no day stamp.
4. Injected post-backup failure does not return EOD success; durable error recorded.
5. Successful EOD produces both pre and post verified packages.
6. Live download refuses/does not serve raw live WAL main-file bytes; serves verified copy.
7. History export fails when DB artifact cannot be verified.
8. Missing/corrupt backup report request returns `BACKUP_SOURCE_UNAVAILABLE` and never labels live data as BACKUP.
9. Migration blocked when snapshot verification fails.
10. Fresh-install and upgrade-on-copy through migration 061.
11. Existing Receiving Book and 5.4.11 security regressions remain green.

## Release Requirements

- Bump every active version reference from 5.4.11 to 5.4.12.
- Additive migration only; do not rewrite prior migrations.
- Do not modify service XML unless an unavoidable deployment requirement appears; prefer no-service-xml package.
- Do not modify real store data in tests.
- Produce `resources-deploy-5.4.12-no-service-xml.zip` only after required checks pass.

## Acceptance Criteria

Complete only when:

- Header-only backups cannot pass health.
- EOD cannot succeed without verified pre and post packages.
- Live download and history export cannot silently ship inconsistent live DB bytes.
- Historical reports cannot present live data as a selected backup.
- Migration cannot proceed without a verified snapshot.
- Verified packages include ops, inventory, attachments, and transfers with manifest.
- All required unit, route, migration, UI build, and release checks pass without skips that hide defects.

## Explicit Non-Goals

- Redesigning unrelated Pulse portals.
- Cloud offsite replication.
- Changing incident or inventory authorization (5.4.13).
- Replacing `xlsx` (5.4.14).
