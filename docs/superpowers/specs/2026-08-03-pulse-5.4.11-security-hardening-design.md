# Pulse 5.4.11 Security Hardening Design

## Goal

Release Pulse 5.4.11 with fail-closed authentication, purpose-bound station and TV authorization, HTTPS-only LAN transport, and non-fatal network-adapter discovery. The release must preserve the 5.4.10 Receiving Book financial controls and must not rely on trusted LAN location, IP addresses, default credentials, or self-asserted station names as identities.

## Scope

This release covers:

- Removal of the default privileged `TRAINING MODE` account and revocation of its sessions.
- Removal of privileged identity details from unauthenticated sync.
- Purpose-bound device authorization for TV, customer-service desk, receiving, and markdown stations.
- Elimination of IP-only authorization and tokenless TV access.
- Consistent `active=1` and `app_access=1` enforcement across session and legacy PIN authentication.
- Correct bootstrap closure when either a Manager or Store Manager exists.
- Removal of the `PC_ADMIN / 1234` legacy fallback.
- Customer-order PII minimization for TV sync.
- HTTPS-only LAN access while retaining loopback HTTP for the Electron desktop.
- Non-fatal network-interface enumeration.
- Security-focused migration, unit, route, device, startup, and Playwright tests.

Backups, immutable incident records, inventory-count authorization, and spreadsheet dependency replacement remain separate releases.

## Chosen Architecture

Pulse will use one centralized request-identity policy. A request may be authorized by:

1. A live staff session whose current database row is active and has application access.
2. A trusted-device token whose persisted purpose permits the requested operation.
3. A secure bootstrap administrator only when no active Manager or Store Manager exists.

Names, source IP addresses, public sync data, and possession of the old default PIN are never credentials.

The existing trusted-device token implementation remains the cryptographic foundation. Migration 060 adds a server-validated device purpose. Capabilities are derived from that purpose in code rather than stored as client-controlled action lists.

## Authentication and Session Rules

### Training Mode

- Fresh installations set `Training_Mode_Enabled` to `0`.
- Startup does not create or reactivate `TRAINING MODE`.
- Migration 060 deactivates any existing `TRAINING MODE` row, sets `app_access=0`, clears its PIN credential, and deletes every persisted session belonging to that identity.
- Disabling training through settings performs the same session revocation immediately.
- Public sync never returns `trainingProfile`, the training PIN, or a training login row.
- Production readiness treats an active or application-enabled training account as a blocking error.
- Historical audit rows attributed to `TRAINING MODE` remain intact.

### Staff and Manager Authentication

- `/api/mobile-auth`, session refresh, PIN-only manager verification, action actor resolution, settings authorization, and daily-rhythm authorization all require the current staff row to satisfy `active=1 AND app_access=1`.
- Revocation takes effect on the next request for both persistent sessions and legacy PIN paths.
- Manager and Store Manager use the same manager-role helper everywhere.
- A disabled identity returns a stable `ACCOUNT_ACCESS_REVOKED` error without revealing whether its PIN was correct.

### Bootstrap Administration

- `PC_ADMIN` is disabled whenever an active Manager or Store Manager exists.
- The legacy `1234` fallback is removed.
- When no manager exists and no secure environment or PIN-file credential exists, Pulse generates a random eight-digit bootstrap PIN and writes it through the existing protected PIN-file path.
- Environment or PIN-file value `1234` remains invalid and blocks production readiness.
- Bootstrap authentication remains rate limited and is disabled immediately after the first Manager or Store Manager is created.

## Public Login and Sync

Unauthenticated sync is a bootstrap shell, not an identity directory.

- It excludes Manager and Store Manager rows.
- It excludes roles, permissions, training metadata, device details, operational records, and customer orders.
- Non-privileged staff names may remain available for the existing staff login selector.
- Manager login uses an explicit name-entry field rather than an enumerable public manager list.
- Authentication responses continue to return role and permissions only after successful authentication.

This design does not treat manager-name secrecy as an authentication factor; it removes unnecessary public enumeration while PIN security, rate limiting, HTTPS, and live account checks remain the controls.

## Purpose-Bound Device Authorization

### Data Model

Migration 060 adds `device_purpose` to `trusted_devices`. Allowed values are:

- `tv`
- `cs_desk`
- `receiving`
- `markdown`

Unknown, blank, or malformed purposes authorize no station action. Existing authorized devices without a purpose do not receive implicit access. Existing token hashes remain stored, but each device must be assigned a purpose by a manager before use.

### Capability Matrix

- `tv`: TV page, TV sync audience, and TV event stream only.
- `cs_desk`: `special_orders` insert and update through the customer-service desk workflow.
- `receiving`: `receiving_mark_arrived`, `receiving_mark_departed`, and `receiving_log_arrival`.
- `markdown`: `kill_dates` insert.

A purpose cannot borrow capabilities from another purpose. Manager APIs may issue, rotate, revoke, relabel, or repurpose a device token and must audit those changes.

### Request Processing

- Device tokens are accepted through the existing `x-device-token` header.
- Tokens are hashed before database lookup and are never persisted in plaintext.
- The raw token is returned once when issued.
- A missing station credential returns HTTP 401 with `STATION_DEVICE_AUTH_REQUIRED`.
- An invalid or revoked token returns HTTP 401 with `INVALID_DEVICE_TOKEN`.
- A valid token with the wrong purpose returns HTTP 403 with `DEVICE_CAPABILITY_FORBIDDEN`.
- A presented invalid token never falls back to another identity mechanism.
- Staff-session workflows remain valid where currently supported.
- Bare `RECEIVING_STATION`, `MARKDOWN_STATION`, and `CS_DESK` names authorize nothing.
- Source IP never authorizes a station or TV.

### Pairing and Upgrade Behavior

The release fails closed immediately. Unpaired clients stop working until a manager uses the loopback desktop application to assign a purpose and issue a token.

The existing Devices settings page gains a required purpose selector and displays a one-time HTTPS pairing URL. The client stores the token locally and removes it from the URL immediately. Revocation takes effect on the next request.

## TV Least-Privilege Contract

- `Require_TV_Device_Token` defaults to `1` on fresh installs and is set to `1` by migration 060.
- `TGP_TOKENLESS_STORE_MODE` cannot override production device-token enforcement unless an explicit test-only mode is active.
- `findAuthorizedTrustedDevice` is called with IP fallback disabled on TV, sync, stream, and station paths.
- “Secure This Store” verifies token-only policy and reports any authorized device that lacks a token or purpose.
- `/tv` requires a valid `tv` token.
- A TV-authenticated `/api/sync` response contains only the minimized `orders_tv` customer-order shape:
  - `order_id`
  - `location`
  - `item`
  - `status`
  - `source`
- TV sync omits full `orders` rows and therefore omits customer names, phone numbers, customer IDs, notes, routes, and staff attribution.
- Public sync contains no live customer orders.

## HTTPS and Network Startup

### Listener Model

- HTTP binds only to `127.0.0.1` and serves the Electron desktop.
- HTTPS binds to the configured LAN host and is the only listener exposed to other devices.
- Public URLs, pairing URLs, and LAN UI links use HTTPS.
- Requests arriving from a non-loopback peer over HTTP receive HTTP 426 with code `HTTPS_REQUIRED` if they reach an explicitly supported compatibility path.
- Credential-bearing requests are never accepted over LAN HTTP.
- CORS allows the loopback HTTP origin and configured private HTTPS origins only.

### TLS Failure

When LAN access is enabled, inability to create credentials or bind the HTTPS listener is a startup/readiness failure. Pulse may keep the loopback desktop available so a manager can view and repair the failure, but it must not advertise LAN readiness or expose a plaintext LAN fallback.

The ready/health response reports actual listener state rather than configured intent.

### Certificate Handling

Pulse continues using the existing locally generated certificate for this release. Certificates are written only under the configured writable data root. Pairing instructions must identify the HTTPS URL and certificate-trust requirement. Certificate generation errors are visible in boot health and the maintenance UI.

### Adapter Enumeration

All calls to `os.networkInterfaces()` are wrapped by a shared safe enumerator:

- An exception returns an empty address list plus a diagnostic warning.
- Startup continues with loopback management available.
- LAN readiness remains unavailable until HTTPS has a usable bind configuration.
- Hyper-V, WSL, internal, malformed, and non-IPv4 entries are excluded consistently.
- Address ordering is deterministic, preferring store-private `192.168`, then `10`, then RFC1918 `172.16-31`.

## Auditing

Manager audit records are required for:

- Training account deactivation performed outside migration startup.
- Trusted-device purpose assignment.
- Token issue, rotation, and revocation.
- Device deletion.
- Secure-store enforcement.
- Bootstrap administrator use and closure.

Audit details include actor, device ID, label, purpose, prior purpose, operation, timestamp, and outcome. Raw PINs and raw device/session tokens must never be logged.

## Error Contract

Stable security errors:

- `ACCOUNT_ACCESS_REVOKED` — 403
- `TRAINING_ACCOUNT_DISABLED` — 403
- `BOOTSTRAP_ADMIN_DISABLED` — 403
- `STATION_DEVICE_AUTH_REQUIRED` — 401
- `INVALID_DEVICE_TOKEN` — 401
- `DEVICE_CAPABILITY_FORBIDDEN` — 403
- `TV_DEVICE_AUTH_REQUIRED` — 401 or a 403 pairing page for `/tv`
- `HTTPS_REQUIRED` — 426
- `HTTPS_STARTUP_FAILED` — boot-health error

Messages identify remediation without exposing credential validity or stored secrets.

## Migration 060

Migration `060_security_access_hardening.cjs` is additive and idempotent. It:

1. Adds `trusted_devices.device_purpose` if absent.
2. Sets `Training_Mode_Enabled=0`.
3. Deactivates and revokes application access for `TRAINING MODE`.
4. Clears the training PIN credential.
5. Deletes training sessions.
6. Sets `Require_TV_Device_Token=1`.
7. Adds any indexes needed for purpose-bound token lookup.

It does not delete staff, audit, order, receiving, financial, or device-history data. Existing devices are not assigned an inferred purpose because historical intent is not deterministic.

## Test Strategy

Every behavior change follows red-green-refactor. Tests must fail for the proven vulnerability before production code changes.

### Unit and Migration Tests

- Fresh install has no active or application-enabled training manager.
- Upgrade deactivates training, clears its credential, and revokes all training sessions.
- Migration 060 is idempotent.
- Manager and Store Manager with `app_access=0` fail every session and PIN-only path.
- PC_ADMIN is unavailable when either manager role exists.
- `1234` fails from environment, PIN file, and legacy-upgrade conditions.
- Secure bootstrap PIN generation succeeds when no manager exists.
- Adapter enumeration exceptions return warnings without throwing.
- Device-purpose capability matrix permits only exact actions.
- Invalid tokens never use IP fallback.

### HTTP Route Tests

- Public sync exposes no privileged rows, roles, permissions, training metadata, live orders, or PII.
- Bare station names receive 401 and mutate no data.
- Correct-purpose device tokens succeed for their exact actions.
- Wrong-purpose tokens receive 403 and mutate no data.
- Revoked tokens fail immediately.
- Tokenless and IP-only TV access fail.
- TV sync excludes customer names, contact details, notes, and full order objects.
- LAN HTTP login, session, action, sync-device, and pairing requests receive 426 or are unreachable because HTTP is loopback-only.
- HTTPS routes accept valid credentials and tokens.

### Startup Tests

- HTTP listener binds to loopback only.
- HTTPS listener binds to the configured LAN host.
- HTTPS certificate or bind failure leaves LAN readiness false and exposes no LAN HTTP fallback.
- Health reports actual HTTP and HTTPS listener state.
- Network-interface enumeration failure does not terminate startup.

### Playwright Tests

1. Public login cannot enumerate Manager, Store Manager, or training identities.
2. A manager can enter their name explicitly and authenticate over HTTPS.
3. The manager assigns `cs_desk` purpose and issues a token.
4. Bare CS desk submission fails.
5. Paired CS desk submission succeeds.
6. Revoking the token blocks the next write.
7. A paired TV loads over HTTPS.
8. Its sync response contains the minimized order shape and no customer PII.
9. An unpaired TV and a device relying only on an authorized IP cannot load operational data.

### Regression and Release Verification

- Existing Receiving Book financial and Playwright workflows remain green.
- Syntax checks and production UI build pass.
- Fresh-install and upgrade-on-copy migration tests pass through migration 060.
- Production readiness fails for insecure transport, training access, default bootstrap PIN, tokenless mode, or IP-only devices.
- All active version sources are bumped from 5.4.10 to 5.4.11.
- The release remains a no-service-XML package unless HTTPS deployment proves an unavoidable service configuration requirement; no service XML will be modified without explicit approval.
- Produce `resources-deploy-5.4.11-no-service-xml.zip` only after all required tests pass.

## Acceptance Criteria

The release is complete only when:

- `TRAINING MODE / 1234` cannot authenticate on fresh or upgraded databases.
- Public clients cannot discover privileged identities or permissions.
- The three station names cannot authorize writes.
- Purpose-bound tokens permit only their intended workflows.
- Tokenless and IP-only TV access are rejected.
- TV responses contain no customer names or contact information.
- Store Manager closes PC_ADMIN bootstrap exactly like Manager.
- `app_access=0` revokes every authentication path.
- LAN credentials and tokens travel only over HTTPS.
- Adapter enumeration failure does not crash Pulse.
- All security, regression, migration, UI, release, and Playwright checks pass without skips.

## Explicit Non-Goals

- Redesigning unrelated Pulse portals.
- Replacing the current session-token format.
- Introducing cloud identity or external certificate infrastructure.
- Repairing backup ordering or backup source integrity.
- Changing incident-investigation immutability or inventory-count authorization.
- Replacing `xlsx`.
